# Desktop client and video

Status as of 2026-11-07, branch `claude/desktop-client-380250`. The client was built against a scripted fake gateway, then run against the real gateway (`internal/gateway`) on `internal/demo`'s drawn phones with scripted agents; see [Against the real gateway](#against-the-real-gateway). The third pass added unlocking with a saved PIN, pairing over Wi-Fi, the companion app, background displays, recordings, export, remote agents and keeping the Mac awake; see [Round three](#round-three). Nothing here touched a real phone.

## What is built

| Path | What it is |
| --- | --- |
| `ui/` | The desktop client on MyGo v0.7.4 native UI. Entry point `ui.Run(api gateway.API, opts ui.Options) error`. It uses nothing of the gateway but `gateway.API`. |
| `ui/fakeapi/` | A scripted `gateway.API`: the prototype's scenarios with ffmpeg test streams for the mirrors. It also has the gateway's extra methods: step screenshots, agents, read-only, deleting history, and round three's pairing, companion app, background displays, drawn recordings, retention and export. |
| `ui/demogw/` | The real gateway on `internal/demo`'s phones, with their drawn screens streamed through `video.FrameStream`, and scripted agents that call it as an MCP client would. For `pinky-ui-demo -gateway` and the end-to-end tests. |
| `internal/video/` | H.264 and HEVC decoding through FFmpeg 9 (libavcodec 63, libavutil 61, libswscale 10) called with purego, VideoToolbox hardware decoding with software fallback, Annex B helpers, a live test stream from the `ffmpeg` command, and a player that decodes on its own goroutine and keeps the newest picture. |
| `cmd/pinky-ui-demo/` | Runs the client against the fake (`go run ./cmd/pinky-ui-demo`) or the real gateway (`-gateway`), a `bench` subcommand for the video numbers, an `e2e` build tag that links MyGo's automation plugin, and `mygo.json` to package it. |
| `assets/` | The brand files (SVG sources, `Pinky.icns`, `pinky.ico`, Linux icons, menu bar template images) and `assets.go`, which embeds the four the client draws. `BRAND.md` lists them. |

```sh
go run ./cmd/pinky-ui-demo -theme dark -dev -approval-timeout 10m -speed 2
go run ./cmd/pinky-ui-demo -scenario three -page settings   # or activity, add-phone
go run ./cmd/pinky-ui-demo -scenario many        # eight phones: All phones and the sidebar scroll
go run ./cmd/pinky-ui-demo -scenario handoff     # the agent asks you to sign in to Dinely
go run ./cmd/pinky-ui-demo -scenario agent       # Codex connects for the first time
go run ./cmd/pinky-ui-demo -scenario companion   # Pixel 9 lacks the companion app: Install
go run ./cmd/pinky-ui-demo -scenario background  # the agent works on a background display
go run ./cmd/pinky-ui-demo -gateway              # the real gateway on internal/demo's phones
go run ./cmd/pinky-ui-demo -gateway -hidden      # starts in the menu bar; the window opens on the first request
go run ./cmd/pinky-ui-demo -gateway -video=false # demo phones without video, as pinky --fake has them
```

With `-gateway`, Claude Code connects to Pixel 9 (fake) two seconds after start, which the gateway asks the person to allow, then opens Dinely, reorders lunch, adds a note and asks to pay. Touch the mirror to take over; it waits with `phone_handoff` until Hand back. The Demo menu starts more agents (a sign-in handoff on the iPhone, Codex for another first connection) and locks or unplugs the iPhone. History and screenshots go to a temporary folder deleted on quit.

Needs Homebrew's FFmpeg 9 (`brew install ffmpeg`): the `ffmpeg` command makes the test streams and its libraries decode them. The **Demo** menu switches scenarios, restarts the one playing (⇧⌘R), plugs in a new phone for Add phone and has the fake phone scan the pairing QR code (it does by itself after 6 s). PINs saved in the demo stay in memory; its agent token is made up. Approvals deny after 60 s, as designed; `-approval-timeout` lengthens that for a slow walk-through.

A walk-through that covers the brief: start with `-scenario three`; watch the Pixel's steps and ripples; Allow (or More options › Deny with a note) on "Pay $12.80?"; click All phones and a tile; Take over on the iPhone, Hand back; hide the window (⌘W) to see the approval panel; click the menu bar icon; Demo › Locked phone and Unlock with Touch ID; Demo › One phone to see the sidebar without "All phones".

## Video

`internal/video` loads `libavutil.61`, `libavcodec.63` and `libswscale.10` with purego: from `PINKY_FFMPEG_DIR`, next to the executable (and `Contents/Frameworks` in the app bundle), then Homebrew's and the system's folders. Missing or of another major version, `video.Load` returns an error that names the file, where it looked and how to install FFmpeg 9 (`video.ErrNotFound`); the client calls it at start, logs it, and every mirror shows it.

The struct offsets (AVFrame, AVPacket, AVCodecContext, AVCodec, AVCodecHWConfig) are FFmpeg 9.0's on 64-bit systems, printed with `offsetof` from Homebrew's headers. `checkLayout` verifies them at load against what FFmpeg itself writes (a frame it allocates, a packet it sizes, a context's codec id and thread count), so another layout fails with a clear error instead of corrupting memory. Pixel formats, hardware device types and decoders are looked up by name. `AVERROR(EAGAIN)` follows the platform's errno.

Decoding:

1. A configuration packet (SPS/PPS/VPS) is held and prepended to the next packet, as scrcpy's client does.
2. With `hw_device_ctx` set to a VideoToolbox device (D3D11VA on Windows, VA-API on Linux), FFmpeg's default `get_format` picks the hardware format, and falls back to software by itself when the hardware refuses a stream. Software decoding uses slice threads only, which add no latency, and `low_delay`.
3. A hardware picture is mapped (`av_hwframe_map`, no copy on VideoToolbox) or else copied (`av_hwframe_transfer_data`). For mirrors and recordings, `Decoder.ConvertYUV` copies its planes as they are, at the stream's size: NV12 from the hardware decoders, I420 from the software one, and pictures in another layout (10-bit HEVC) converted to I420 by `sws_scale_frame`. It names the matrix swscale reads from the stream's tag: BT.601 for a stream that names none, BT.709 for one whose matrix swscale cannot convert (the Mi 10 Pro's YCgCo). `Decoder.Convert` converts to RGBA with `sws_scale_frame`, into an `image.RGBA` of any size, for the gateway's screenshots from video (`internal/gateway/frameshot.go`) and the bench, 10-bit pictures too (`TestConvertTenBit`).
4. `video.Player` decodes on a goroutine of its own and triple-buffers: the picture on screen, the newest one waiting, the one being converted. A player that falls more than 30 packets behind skips to the next key frame. While nobody takes pictures for a second (the window is covered or the screen locked, so it paints nothing), it goes on decoding but converts nothing.
5. The mirror element takes the newest picture in its `Draw` callback, hands its planes to `Bitmap.UpdateYUV` (MyGo's, from egoist/mygo#1487: NV12's planes are taken without a copy, I420's chroma is interleaved into a plane the bitmap keeps, a picture of the same size keeps the textures, and the GPU converts and scales the planes as it samples them) and asks for the next paint with `AnimationFrameRate(60)`. So video frames repaint the window without rebuilding the view, and nothing is converted while the window is hidden. Recordings play the same way. A screenshot from the mirror copies the planes on the main thread and converts them to RGBA off it (`video.YUV.RGBA`, as MyGo's CPU renderer converts them), at the phone's full resolution.

Until 2026-11-08 pictures were converted to RGBA by libswscale at the pixel size they were shown at (the bezel's screen box times the display scale): about 600×1332 for a 1080×2400 stream shown 300 points wide on a 2× display, and 316×700 for All phones' tiles. The planes go over at the stream's size instead: copying them costs a fifth of scaling them, and the GPU samples them bilinearly, two taps each way, as libswscale's fast bilinear scaled them. MyGo makes no halved copies of YUV pictures (its author's answer on #1487: apps pass frames at the size they show), so a mirror shown at a quarter of its stream or less would alias more than it did; the smallest tiles are about a third.

### Measurements

Machine: Apple M4 Pro (14 cores), macOS 27.2, Homebrew FFmpeg 9.0.2 (libavcodec 63.1.102). `go run ./cmd/pinky-ui-demo bench` decodes ffmpeg test streams (testsrc2 or testsrc; libx264 ultrafast or hevc_videotoolbox; 8 Mbit/s, a key frame each second, no B-frames) in real time at 60 fps, 15 s per run after 3 s of warm-up. CPU is the process's user and system time over all its threads, as a share of one core, plus VideoToolbox's decoder service, which decodes in a process of its own. Latency runs from the packet reaching the player to its RGBA picture being ready; the GPU upload and the display's refresh come on top.

| Stream → picture | Decoder | CPU, process + VT service | Packet → RGBA, median / p95 | Decode + convert, means |
| --- | --- | --- | --- | --- |
| H.264 1920×1080 → 1920×1080 | VideoToolbox | 6% + 3% | 2.2 ms / 3.5 ms | 2.3 ms + 0.36 ms |
| H.264 1920×1080 → 1920×1080 | software | 15% | 0.74 ms / 1.0 ms | 0.44 ms + 0.32 ms |
| H.264 1080×2400 → 1080×2400 | VideoToolbox | 29% + 3% | 4.3 ms / 4.9 ms | 2.2 ms + 2.3 ms |
| H.264 1080×2400 → 600×1332 (a mirror at 2×) | VideoToolbox | 15% + 3% | 3.2 ms / 4.0 ms | 2.3 ms + 1.1 ms |
| H.264 1080×2400 → 600×1332 | software | 22% | 1.3 ms / 2.0 ms | 0.40 ms + 1.1 ms |
| H.264 1080×2400 → 1080×2400 | software | 23% | 1.4 ms / 2.0 ms | 0.37 ms + 1.1 ms |
| HEVC 1206×2622 → 600×1304 | VideoToolbox | 16% + 3% | 3.5 ms / 3.9 ms | 2.4 ms + 1.2 ms |
| HEVC 1920×1080 → 1920×1080 | VideoToolbox | 6% + 3% | 2.1 ms / 3.5 ms | 2.1 ms + 0.29 ms |

About 4 of 900 pictures were replaced before they were taken, all at the start, when ffmpeg sends its first half second at once.

What the numbers say:

- **1080p60 costs about 9% of one core with VideoToolbox, and a picture is ready 2.2 ms after its packet.** FFmpeg waits for VideoToolbox frame by frame, which is most of that.
- **Converting to RGBA is most of the CPU.** VideoToolbox hands over NV12, which libswscale converts at about half the speed of YUV420P from the software decoder (it seems to miss the fast path), so at a phone's full size software decoding is both cheaper (23% against 32%) and quicker (1.4 ms against 4.3 ms) on this machine. At the size a mirror shows, where scaling dominates, both cost about the same. Hardware decoding stays the default: phones' real screens are harder to decode than test patterns, and smaller machines lean on the decoder more.
- **Two conversion threads** halve the conversion time for no more CPU: at mirror size, one thread took 15% and 2.1 ms a picture, two 14% and 1.0 ms, fourteen (libswscale's automatic choice) 20% and 0.4 ms. The decoder uses two (`DecoderOptions.ConvertThreads`).
- **Converting at the shown size matters:** a 1080×2400 stream shown at 600×1332 costs half the CPU of converting it whole.
- **Not measured:** the upload in `Bitmap.Update`, painting, and the whole client's CPU while it mirrors. The screen was locked for most of this overnight session, and macOS draws no windows then, so the client paints nothing. Earlier interactive runs played smoothly; Activity Monitor next to `go run ./cmd/pinky-ui-demo` shows the client's share.

Ways to cut the CPU further, in the order I would try them: ask VideoToolbox for planar YUV or BGRA output through `hw_frames_ctx` (needs a `get_format` callback through purego), which removes the slow NV12 path or the YUV conversion; MyGo's NV12 or I420 bitmap updates converted in a shader (the design's first upstream ask); and zero-copy CVPixelBuffer to Metal (#973). The second is done (below); MyGo's author left the third for later.

### Planes instead of RGBA (2026-11-08)

The same machine and bench, with and without `-yuv`, two runs each, for a 1080×2400 H.264 stream at 60 fps shown at 600×1332:

| Handing a picture to MyGo | Decoder | CPU, process + VT service | Packet → picture, median | Convert or copy, mean |
| --- | --- | --- | --- | --- |
| RGBA at 600×1332, `Bitmap.Update` (before) | VideoToolbox | 17–18% + 3% | 3.5 ms | 1.2 ms |
| Planes at 1080×2400, `Bitmap.UpdateYUV` | VideoToolbox | 4% + 3% | 2.4 ms | 0.12 ms |
| RGBA at 600×1332, `Bitmap.Update` (before) | software | 25–26% | 1.7 ms | 1.2 ms |
| Planes at 1080×2400, `Bitmap.UpdateYUV` | software | 12% | 0.58 ms | 0.15 ms |

Drawing costs the main thread a little more: MyGo's Metal renderer encodes a full-size NV12 picture, its upload included, in 0.43 ms of CPU, against 0.28 ms for an RGBA picture of 600×1332 (its offscreen bench, measured for egoist/mygo#1487), and I420 from the software decoder costs another 0.25 ms to interleave its chroma. At 60 fps a mirror then takes about 7% of a core with VideoToolbox instead of 19%, and about 16% in software instead of 27%, besides VideoToolbox's service. Not measured: the whole client with a window showing the mirror. MyGo's `TestDrawsVideoAsTheCPURenderer` checks on this Mac that Metal draws NV12 planes as its CPU renderer does, and captures of `pinky-ui-demo` over the automation socket, which MyGo draws on the CPU, show the demo's video in its colors. `TestMirrorShowsPlanes` plays a phone through the mirror as a USB stream (H.264, 30 fps) that ends and opens again as a phone moving to Wi-Fi or Tailscale does, at another size, in HEVC at 15 fps and 1 Mbit/s: each shows in the colors ffmpeg made, within 3 levels, at its aspect, also between the slower stream's pictures, and a screenshot has the stream's size.

## How the client reads gateway.API

`gateway.API` leaves some things to convention. The client assumes these; the fake follows them, and the gateway should too (or tell me what to change):

- **Device coordinates.** A mirror opens `Stream` with `MaxSize: 0` and takes the decoded picture's size as the device's coordinate space: touches are sent in those pixels (as `driver.Toucher` defines them since 5e83552; `Key` and `Text` carry no coordinates) and steps' `Target` and `Point` are drawn in them. On an iPhone screen pixels and picture pixels differ by about 1%, so the overlay is clipped to the screen and an outline at the edge cannot spill onto the bezel. That matches the design, where screenshots are decoded from the stream. Tiles open the stream at full size too and scale it down while converting, so their overlays stay right without a `DeviceView` screen size.
- **Step marks.** Status `approval_pending` is "waiting for you" (amber dot); status `user`, or no tool and text starting "You ", is the person's step (person icon); status `""` or `running` on the last step of a running task is in progress (green pulse, and the mirror draws its touch); everything else is done (check). A step's text may hold a second line after a newline, shown smaller ("Your note: …").
- **Outcomes.** A done task with a "You denied" step (or status `approval_denied`) ended "after your answer", shown as Denied in Activity unless something was allowed after it.
- **Summaries and app icons.** Activity shows the `summary` the agent gave `phone_release` (any step's `Args` with a `summary` field), and takes the app for the letter icon from the first `phone_launch` step's `app` argument, or an "Opened X" step.
- **Approvals.** `Decide` gets `allow_once`, `allow_task`, `allow_always`, `deny` (with the note) or `take_over`. The approval card names the rule in "Always allow *payments* in *Dinely*" from `NeedView.Rule` and `App`, and offers it only when `NeedView.AlwaysAllow` is set (the gateway can keep it), and Allow for this task only when `NeedView.AllowTask` is set (not on the agent's own questions), in both the card and the floating panel; Settings › Safety › Always allowed lists the kept answers (`Exemptions`, `RemoveExemption`). `NeedView.Screenshot` must be in the same pixels as `Target`.
- **Input.** Pointer down, move (throttled to 125 Hz) and up go to `Touch`; right click is Back and middle click is Home; the wheel and the touchpad become a finger dragging the content (down at the pointer, moves against the scroll, up 140 ms after the last event, lifted and put back at the edges); Enter, Tab, Backspace, Delete, Escape, the arrows and Page Up/Down go to `Key`; typed and input-method text goes to `Text`; ⌘V pastes the computer's clipboard as text. The gateway is expected to pause the agent on any of them (the API's comment says so); the client shows the banner when the device reports `in_control`, or while a handoff is open on it. Calls run off the main thread, one queue per device, so they keep their order.

## Gaps in gateway.API (for the main session)

None of these block the demo; each is a small additive change when the gateway is ready for it. I did not change `api.go`. The gateway's methods beyond `gateway.API` (`MediaPath`, `Agents`, `SetAgentScope`, `SetReadOnly`, `WipeHistory`, and round three's in `internal/gateway/extras.go`) are used through optional interfaces, see below. `ui/contract_test.go` fails to compile when one of them stops matching the gateway's signature.

- **Settings.** No methods to read or change the safety preset, blocked apps, unlock, code hiding, retention or recording. The client keeps them (`ui.Options.Settings`) and reports each change through `ui.Options.OnSettings(old, s)`, with the settings as they were before it, and `cmd/pinky` passes on what differs and persists them. What the gateway keeps of them (the preset, Read-only mode, Hide codes, the blocked apps) comes again from `ui.Options.GatewaySettings` while Settings shows, once the policy's version changed (a hand edit of the rules files, or a change from Settings); it is shown and becomes the next change's `old`, so a change never passes on a value that a hand edit replaced. A read that a change overtakes is dropped and made again. A rules file without a preset shows none of the three.
- **Pairing.** Android pairs by QR code or pairing code through the extras (round three). iPhone pairing with a code still has no method: Pair waits for the gateway to report the iPhone.
- **Unlock.** `Unlock(deviceID)` is called after the person clicks "Unlock with Touch ID"; the gateway asks the keychain for the PIN, which asks for Touch ID. The client only saves and removes PINs.
- **Rules file path.** `ui.Options.RulesFile` opens it from Settings › Advanced.
- **Phone controls.** Record screen (a manual recording) and Rotate have no API; they show disabled.
- **One task's history.** Activity's per-task Delete stays disabled: the gateway can only wipe all of it.
- **Remote agents' state.** The client cannot tell whether the HTTP server listens (a port in use, say); `cmd/pinky` could report it.

## Against the real gateway

The second pass (2026-11-07) ran the client against `internal/gateway` itself and closed the gaps it showed. `go run ./cmd/pinky-ui-demo -gateway` is the way to see it; `go test ./ui -run TestGateway` clicks through it.

**What changed**

- **Handoffs** (`NeedHandoff`): the agent called `phone_handoff` and waits. The card's title is the agent's reason. Done → `Decide(id, AllowOnce, note)` (hand back with the note), Take over → `Decide(id, TakeOver, "")`, Decline → `Decide(id, Deny, note)`; Add a note opens the note field for Done and Decline. The floating panel and the flyout show handoffs too; the panel has no Return and Esc for them, since their buttons are not Allow and Deny.
- **First connections** (approval with rule `New agent`): a card with "Let *agent*", a select of what it may do (All apps except blocked ones, Only the apps I choose with an apps field, Read only: browse, never commit, Watch only: no taps or typing) with a line under it that says what the chosen one allows, Deny and Approve. When the agent asked for a read-only task (`NeedView.ReadOnly`), the card says so and the select starts on Read only. It shows in Needs you, in the floating panel and at the top of Settings › Agents, with an amber dot on the Agents tab.
- **The gateway's extra methods**, found with type assertions on the API value (`ui/extras.go`), so `gateway.API` is unchanged and the client still runs on anything that only implements it: `MediaPath` for step screenshots (task cards, Activity thumbnails and previews, replay); `Agents` and `SetAgentScope` for Settings › Agents (reloaded every 5 s while shown, and at once when a first-connection request opens or closes); `SetReadOnly("", on)` when the Read-only switch changes; `WipeHistory` behind Settings › Privacy › Delete…, with a confirmation.
- **In control without a task**: the banner reads "You're in control. Hand back to let agents use this phone again." and Hand back calls `HandBack`; the All phones tile shows Hand back on hover too.
- **`ui.Options.Hidden`**: on macOS the app starts as an accessory (menu bar icon, no Dock icon, no window); the first Needs you item opens the main window without taking the keyboard (`ShowInactive`) and makes the app regular. Opening it from the menu bar does the same.
- **App Nap**: `ui.Run` holds an `NSProcessInfo` activity for the app's lifetime (then `ui/appnap_darwin.go`, purego's objc; since 2026-11-08 MyGo's `Power.KeepRunning`, `keepRunning` in `ui/power.go`; a no-op elsewhere).

**Decisions**

1. **App Nap flags.** The brief asked for `NSActivityUserInitiated | NSActivityLatencyCritical`. `NSActivityUserInitiated` includes `NSActivityIdleSystemSleepDisabled`, so holding it for the app's lifetime would keep the Mac from ever idle-sleeping while Pinky runs, and Pinky lives in the menu bar all day. I used `NSActivityUserInitiatedAllowingIdleSystemSleep | NSActivityLatencyCritical`: App Nap, timer coalescing and background throttling stay off, which is what slowed the streams, and the Mac may still sleep when idle. Round three adds `NSActivityUserInitiated` while a task runs (round three, item 7). Since 2026-11-08 MyGo's `Power.KeepRunning` (egoist/mygo#1486) holds `NSActivityUserInitiatedAllowingIdleSystemSleep` without `NSActivityLatencyCritical`, which nothing measured needed. Measured on macOS 27.2, an app with no activity is napped after 35 to 40 s with its windows out of sight, but not while its menu bar icon shows, so Pinky naps only where the menu bar is out of sight too, as behind the locked screen; `Power.KeepAwake` also keeps App Nap off, but keeps the Mac awake as well.
2. **The scope chosen for a new agent.** Approve calls `SetAgentScope(name, scope)`, which also approves the agent, and then `Decide(id, AllowOnce, "")`, so the person's choice wins. The gateway's `approveAgent` currently sets `DefaultScope` again when a call that was still waiting picks up the answer; the main session asked the gateway session to keep a scope already set instead. Until that lands on main, a narrower scope chosen in the card can be lost on the first approval; the client does not poll to put it back. `TestGatewayAgentScope` checks the order of the two calls.
3. **The request's detail.** The gateway's "Allowing gives it everything access." would contradict a narrower choice in the select, so with the select shown the client drops that sentence and adds the time ("Asked at 03:51.").
4. **A handoff on a locked phone** is one card: the handoff's reason, "Unlock with Touch ID" (which ends the handoff, as decision 11 says), and Decline and Done for after an unlock on the phone. The separate unlock card for that phone is hidden, so two amber cards never ask for one thing.
5. **A handoff outranks control.** The gateway reports `needs_you` for a phone with an open handoff even while the person is in control (the agent waits with `phone_handoff` after it got `user_took_over`). So the phone screen shows the banner whenever a handoff is open: "You're in control. *Agent* is paused." when the task is paused, else "Your turn. *Agent* waits for you: *reason*". Hand back answers the handoff through `HandBack`. When the person already holds the phone, the card says "You're in control. Click Done to hand the phone back" and offers Decline instead of Take over.
6. **Step wording** now reads the gateway's conventions as well as the fake's: "Waiting for you: Tapped “Pay”" waits as "Waiting for you: tap “Pay”", then reads "You denied: tap “Pay”" (`approval_denied`), "Tap “Pay”" with "Not done: you took over" (`user_took_over`), "… stopped", "… the agent did not come back for it" (`expired`); handoffs read "Asked you to take over: …", then "You handed it back" or "You declined" with "Asked: “…”"; `ask` steps read "You agreed" or "You said no"; failures name their code. `device_locked` no longer marks a step as waiting: the gateway's locked phone is an unlock need, not a step. Between the person's answer and the end of the action, the gateway keeps the step `approval_pending` while the task is already working again; the client words that as "You answered: tap “Pay”" instead of showing an amber step with no card.
7. **Step screenshots** load with `MediaPath`, `os.ReadFile` and `image.Decode` off the main thread, at most 400 kept. The target is outlined on a screenshot only when the phone's live picture size is known (the gateway scales screenshots down by a whole factor), and never on 54-point thumbnails, where it said nothing.
8. **Read-only** calls `SetReadOnly("", on)` from the switch as well as reporting the change through `OnSettings`. If `cmd/pinky` also applies it, the two calls agree.
9. **Demo phones get video** through `video.FrameStream`, which encodes `Screenshot()` twelve times a second with the `ffmpeg` command. `ui/demogw` wraps `internal/demo`'s provider for that, so the gateway still sees the demo's `Toucher` and `PersonWatcher`.

10. **The mirror's states.** The first picture is taken while the mirror paints, and painting does not build the view again, so the "Connecting…" overlay from the build before it stayed over the live picture until something else changed (an idle iPhone sends no frames while its screen is still). Taking the first picture now asks for a build. A stream that fails shows why ("This phone has no live picture." for `ErrUnsupported`) and is opened again after 3 s (2 s after it ends) on a timer, not on the next build, which an idle window or a locked screen never makes. While it tries again the mirror keeps showing that reason, not the Connecting spinner, so a phone without a picture does not flicker every 3 s. Updates that goroutines post before the main window exists are kept and run once it does, instead of being dropped.

**For `cmd/pinky` (main session)**, done on main since: `Hidden` from `pinky mcp` (`--background`), and demo phones streaming through `video.FrameStream` in `internal/demo`.

- With `TrustNewAgents: true` in `--fake` mode the first-connection card never shows; leave it false in app mode if people should see it.
- Gateway wording seen on the way: the payment approval's title is "Pay: “Place order · $12.80”?" where the prototype says "Pay $12.80?", and the first-connection detail says "everything access".

**Decisions**

1. **Where the PIN is saved.** In Settings › Phones and on the locked phone's card, the same form, at least four characters. The mirror's lock has no Unlock button of its own: inside the mirror's input handler it took clicks unreliably, and it repeated the card.
2. **Is there a keychain?** `secret.Supported` asks the store, which says so without asking the person anything; no store is probed by writing or deleting.
3. **Where exports go.** A new folder on the Desktop per export ("Pinky activity 2026-11-07 at 09.30.12"), shown in the Finder, as screenshots go to the Desktop. No save dialog, which a locked screen could not test either.
4. **The agent's display is for watching.** Input there would reach the phone's own screen, so the keys are disabled with a tooltip and touches are not taken; the person switches to the phone's screen to use the phone.
5. **A recording's position** comes from the frames' PTS, which `recording.Open` is expected to count from the recording's start, as `RecordingMark.At` does. A stream that counts from where it opened (its first PTS far below the start asked for) is offset.
6. **Record and Keep activity reach the gateway from the client**, through `SetRecording` and `SetRetention`, so they apply whether or not `cmd/pinky` passes them too; the calls agree.
7. **The agent token comes from `Options.AgentToken`**: the client reads no files of the gateway's.
8. **The companion card** sits above Tasks in the neutral panel color, not amber and not in Needs you: nothing waits on it.

## i18n

The client speaks English, Simplified Chinese (2026-11-07, branch `claude/ui-zh-hans-465ea6`) and Japanese (2026-11-09, DIYgod/pinky#1 by tarou-jp, brought up to date with main). Everything the person sees in the app is in the catalogs: the windows, the floating approval panel, the menu bar flyout and the tray, the menus, notifications, toasts, tooltips and accessibility labels. What agents read (MCP tool descriptions and results, `docs/SKILL.md`, `docs/mcp.md`) stays English.

**How it works.** MyGo's catalogs (`docs/i18n.md` in the MyGo module): `cmd/pinky/mygo.json` has `"i18n": {"dir": "locales", "source": "en"}`, so `cmd/pinky/locales/` holds `en.json` (every message, with an `@key` description and typed placeholders), `zh-Hans.json` and `ja.json`, in ARB with ICU MessageFormat. `go tool mygo generate cmd/pinky` (which `mygo build` and `mygo dev` also run) writes `catalog_gen.go` there: a Go function per message, named after its key (`sidebarStopAll` → `locales.SidebarStopAll()`), which says it in the language the app shows. The `ui` package calls them; the generated code embeds the catalogs and imports MyGo's own Simplified Chinese and Japanese strings (the menus by role, the Edit and Window menus, Quit, text fields' menus, dialog buttons). A packaged build declares every catalog's language (`CFBundleLocalizations`, `zh-Hans.lproj`, `ja.lproj`), so System Settings › General › Language & Region › Applications lists Pinky; `cmd/pinky/resources/darwin/<lang>.lproj/InfoPlist.strings` translate what Info.plist says to the person (the reason for Local Network access, `NSLocalNetworkUsageDescription`), and a new language needs one.

**Which language.** MyGo picks the one of the app's languages the person reads best, from the system's preferred languages in order (any Chinese written in simplified characters, such as zh-Hans-CN or zh-Hans-SG, gets Chinese; ja and ja-JP get Japanese; Traditional Chinese and everything else get English). Settings › Advanced › Language overrides it: System, English, 日本語 or 简体中文 (each named in its own language, as `i18n.Autonym` writes it). The choice applies at once, without a restart, and MyGo keeps it as the app's language in the macOS defaults (`AppleLanguages` of the app's domain), which System Settings shows too; System clears it. For one run, `MYGO_LOCALE=zh-Hans` forces a language and saves nothing (`go tool mygo dev -lang zh-Hans` does the same). The e2e build in Chinese:

```sh
go build -tags e2e -o build/pinky-e2e ./cmd/pinky
mkdir -p /tmp/pkzh && PINKY_HOME=/tmp/pkzh MYGO_AUTOMATION=/tmp/pkzh/auto.sock MYGO_LOCALE=zh-Hans build/pinky-e2e --fake
```

**The gateway's words.** The gateway records steps, approval titles and status lines as finished English ("Tapped “Pay”", "Pay: “Place order · $12.80”?", "Claude Code · Reorder lunch · in the background"), and history keeps them that way. In Chinese and Japanese, `ui/gwtext.go` reads them back by the patterns of `internal/gateway` (`describe`, `approvalTitle`, `statusLocked`, the files and agent steps) and says them with the catalog's `gw…` messages; `stepDisplay` words the client's own step states (`step…`), and `ruleName` and `ruleAction` name the policy's rules. A step's second line is read the same way, by `stepSub`: "Your note: …", and "Always allowed: “Payments” in Dinely" under a step that ran without asking because of the person's Always allow, which an uncertain step keeps under "May have happened". Inside them, agents' words (task titles, handoff reasons, questions, notes, summaries) and the phone's (labels in quotes, app and phone names) stay as they are. Text that matches no pattern shows in English, and in English the gateway's text always shows unchanged. When the gateway words something new, add a pattern and a case to `ui/gwtext_test.go`. `internal/update`'s reasons why a copy of Pinky cannot replace itself (`Location.Problem`) are read back the same way, by `whereProblem`.

**Adding a message.** Add it to `en.json` with an `@key` description (where it shows, what its placeholders hold; `type` is `String`, `int` or `DateTime`), then its translations to `zh-Hans.json` and `ja.json` in the same commit (and recheck both when the English changes), run `go tool mygo generate cmd/pinky`, and call `locales.Key(…)`. Name keys after the area they belong to (`settingsPrivacy…`, `needs…`, `tasks…`), and make one message of a sentence with placeholders rather than gluing pieces, so a translation can reorder it; counts that change the English words are ICU plurals. `go test ./cmd/pinky/locales` fails when a key lacks a translation or a translation's arguments differ; `go tool mygo i18n check cmd/pinky` reports the catalogs' errors and warnings. Strings that sessions add in English work as before and show in English in the Chinese and Japanese UI until they get keys.

**Chinese style.** Short, plain Simplified Chinese as in Mac apps, addressing the person informally; full-width punctuation, a single-character ellipsis, a space between Chinese and Latin letters or digits, and the terms `zh-Hans.json` already uses (look a term up there before adding one). Product and feature names that are names stay as they are (Pinky, Claude Code, Touch ID, Pinky Companion, Wi-Fi, USB).

**Japanese style.** Polite, plain Japanese as in Mac apps (です・ます), with the terms `ja.json` already uses: スマホ for phone, パソコン for computer, エージェント, タスク, 「設定 › スマホ」. 「」 quote the app's and the systems' names for menus, buttons and settings; “” keep the quotes around the person's and the phone's words that English has (“{label}” をタップ). Full-width punctuation, a single-character ellipsis, and a space between Japanese and Latin letters, digits or placeholders. Name the phones' settings as their Japanese systems do: iOS's デベロッパモード, 「プライバシーとセキュリティ」, 「このコンピュータを信頼しますか？」; Android's 「開発者向けオプション」, 「USBデバッグを許可しますか？」, 「ペア設定コードによるデバイスのペア設定」, 「QR コードによるデバイスのペア設定」, 「IP アドレスとポート」; Finder's 「Wi-FiがオンになっているときにこのiPhoneを表示」. **Tests.** The `ui` tests pin the client's words to English (`ui/main_test.go`), since they find controls by their English labels; `inLanguage(t, "zh-Hans", testers…)` switches a test to Chinese, as `TestGatewayWordsInChinese`, `TestStepDisplayInChinese` and the language setting's test do (`TestLanguageSetting` picks 日本語 too, and `TestLanguageFollowsAJapaneseSystem` reads Pinky on a computer that prefers Japanese). The floating panel used to show a strip 100 points high around the target, scaled to the target's width: for a small button that was the button alone, enlarged, and the person could not tell the app, the page or what the agent wanted to press. It now shows, from `ui/approvalshot.go`:

## Brand colors, and keeping amber and red apart

The prototype's colors stay, quiet as they were: neutral grays, indigo for primary buttons, links, switches and the agent's overlay, amber for what needs the person, red for Stop, green for working. The brand appears only where the eye looks for identity:

- **Logo:** the 32-point icon (`pinky-32.svg`, lemon field, phone face, watermelon ring) in the sidebar header, next to the name, right of the window controls. Lemon appears nowhere else.
- **Selection:** the selected row of the sidebar, Settings' sections and Activity keeps the prototype's gray fill and gains a 3-point watermelon bar at its start.
- **Focus:** the keyboard focus ring is watermelon (`#EE4D6C` light, `#FF8A9B` dark; 3.6:1 and 7.6:1 against the background).

The prototype's amber and red sat too close to the brand. In OKLCH, dark mode's amber `#F2BB59` (L 0.82, hue 80°) was almost the logo's lemon `#FFBE1A` (L 0.84, hue 83°), and dark mode's red `#FF8A80` (hue 26°) had the same lightness as the watermelon highlight `#FF8A9B` (hue 12°). So I moved the semantic colors away from the brand's hues, and kept each color to its own shapes:

| Role | Light (was) | Dark (was) | OKLCH hue |
| --- | --- | --- | --- |
| Needs you: dot | `#DF8601` (`#E09100`) | `#F7A74E` (`#F2BB59`) | 65° (lemon is 83–96°) |
| Needs you: text | `#975800` (kept) | `#F7A74E` (`#F2BB59`) | 64–66° |
| Needs you: card, line, tile edge | `#FFF6EB`, `#F6D7B1`, `#E79733` | `#342210`, `#674520`, `#B6762A` | 66–72° (were 83–85°) |
| Stop: text, border, hover | `#C32C18`, `#F0C6BD`, `#FEF0ED` | `#F87A60`, `#723B31`, `#3A1E19` | 31–33° (watermelon is 11–13°) |
| Brand: selection bar, focus ring | `#EE4D6C` | `#FF8A9B` | 13° / 12° |

The trade-off: amber now leans orange and red leans vermilion, so amber and red are closer to each other than in the prototype (hue 65° against 31°, but lightness 0.70 against 0.54 in light mode), still clearly apart, while neither can be mistaken for the logo or the selection mark. Shapes back the hues up: amber is dots, card tints and the tile edge; red is only the text and border of Stop; watermelon is only a thin bar and the focus ring; lemon is only inside the logo. No brand color is used as a fill, so selected rows never look like Needs you cards.

## Known issues

- Unpackaged builds (`go run`) show no notifications; macOS allows them for packaged apps only. The packaged demo (`go tool mygo build cmd/pinky-ui-demo`) builds, signs ad hoc and starts its streams, but its notifications were not tried: the screen was locked by then, so nobody could answer macOS's permission question.
- The approval panel shows when approvals wait and the main window is not focused. While Pinky itself is the active app with only the panel and the flyout open, macOS may make the panel the key window when the main window hides; it never takes the keyboard from another app.
- `Painter.AnimationFrameRate(60)` repaints the window at 60 fps while a mirror plays, even when the picture is still. A later step is to repaint only when a new picture arrives.
- While the screen is locked MyGo draws nothing, so a window builds its view only when something asks it to (the automation socket's input, a capture). The client reads the gateway's views before its window shows, so the first frame already has the phones.
- Wheel scrolling maps a notch to 2.5× its DIPs of finger travel; touchpads map one to one. Tune on real phones.
- The panel's Return and Esc work only after the person clicked it, by design.
- Windows and Linux builds compile but were not run; D3D11VA and VA-API decoding are untested.
- FFmpeg 9 only; other major versions are refused rather than supported with other offsets.
- Approving a new agent with a narrower scope can lose it on the first approval until the gateway keeps a scope set before the answer (decision 2 above); 79d1c2a on main fixed this in the gateway.
- Recordings, export, retention and background displays are stubs in the gateway, so against it the client shows its fallbacks; the player and the agent's display were checked on the fake only (the player through the real decoder).
- Keeping the computer awake while tasks run was tried on macOS only; Windows and Linux get MyGo's power requests, untried there.
- Durations ("38 s", "1 min 02 s") are joined with no-break spaces, so a task card's "Claude Code · sdk_gphone64_arm64 · 38 s" moves "38 s" to the next line together instead of leaving the "s" alone. MyGo honors them (`TestDurationsDoNotWrap`), except that a no-break run wider than its whole box still breaks inside, as browsers do.
- With `-hidden`, the first request opens the main window and, because that window is not focused, the floating panel as well.
- `video.FrameStream` costs a full-size RGBA copy and an x264 encode per frame; it is for demo phones only.
- **Automation with the screen locked was unreliable until MyGo fixed it.** While the screen is locked a window counts as occluded and MyGo holds its frames (`engine.holdFrame`). In a 15-second run the main window was built twice, once at start and once on the first capture; a press (`act`), a pointer click (`input`), pointer moves and later captures built nothing. A press only bumps the button's click count, which the next build consumes, so it was lost until a build happened to come along, and which presses "worked" depended on timing, not on the card: Approve, Allow and the sidebar's Activity were lost the same way. The floating panel is built once when it is made (hidden, nothing waiting) and never again while the screen is locked, so its capture was an empty card with an empty tree. Since 2026-11-08 Pinky uses a MyGo whose automation builds the frame a window out of sight waits for when it acts on it, reads its tree, waits for it to idle or captures it (egoist/mygo#1485): in `pinky-ui-demo -hidden`, whose window never shows, a press on the sidebar's Settings over the socket shows Settings in the next tree and capture. `idle` still never settles while a mirror plays, as it repaints 60 times a second. `ui.Tester` builds every frame and stays the way to test these flows in unit tests (`TestGateway*`, `TestApprovePaymentWithRealGateway`).

## Removing a phone

**Remove this phone…** (`ui/removephone.go`) is in the ⋯ menu under the mirror, on the page of a phone that is offline or needs setup (a link under its detail), on each tile in All phones (a ⋯ button that shows while the pointer is on the tile, and the tile's right-click menu), in a phone's right-click menu in the sidebar, and on each phone's row in Settings › Phones ("Remove…"). Every entry opens one dialog, which says:

- what goes: the phone leaves the list and agents can no longer use it; its saved PIN and its settings in Pinky are deleted; the task running on it stops (with the agent's name and the task);
- what stays, unless the person ticks **Also delete its history: tasks, screenshots and recordings** (off by default): its history in Activity;
- what happens next, by how the phone is connected now: on a cable it shows up again at once as a new phone, unless unplugged first; an Android phone on Wi-Fi is disconnected and not reconnected by itself, and comes back when paired again in Add phone or plugged in; an iPhone on Wi-Fi comes back when plugged in; an offline phone comes back when plugged in (or, on Android, paired again over Wi-Fi). And that the phone keeps trusting the computer, so other apps are not affected: Pinky offers no way to unpair an iPhone.

**Remove** (red) calls the gateway's `RemoveDevice` and, once the phone is gone, deletes `pin:<id>` from the keychain; a missing PIN or a system without a keychain is fine. The dialog stays open, with a spinner, until the gateway answers; an error shows in it. Afterwards a toast says "Removed <name>", or that the history or the PIN could not be deleted; the client forgets what it kept about the phone (PIN state, background switch, companion state, the connection choice Settings › Phones read, its popovers), and reloads Activity when the history went. The selection moves to another phone (`afterRefresh`). Without `RemoveDevice` on the API (an older gateway), none of the entries show. The fake removes phones too (`fakeapi/remove.go`, `Removals`, and `SetTransport` to put a phone on a cable or on Wi-Fi).

Strings: the `removePhone*` keys in both catalogs. Tests: `ui/removephone_test.go` (each entry, the notes for a cable, Wi-Fi and an offline phone on both platforms, the history box, Cancel, the PIN deleted, Chinese) and `TestRemovePhoneInTheApp` in `cmd/pinky` (tag `e2e`: the app over the automation socket with the fake phones). `PINKY_SCREENSHOTS=dir go test ./ui -run TestRemovePhoneScreenshots` draws the dialog and its entries in English and Chinese (`remove-*.png`).

How the banner works now (`ui/phone.go`):

- It is the first child of the middle column, before the phone. ## All phones with many phones (2026-11-08)

All phones scrolls, and its tiles sit in columns (`allPhonesGrid` in `ui/phone.go`). Before, the tiles were a wrapping row in the middle of the page: more phones than the window showed were out of reach (the row overflowed without a scroll view, and tiles squashed to nothing in a narrow window), and a last row that was not full sat centered, its tiles wider than those above.

- The page is a scroll view under the header, between the sidebar and the right panel, which stay put. The tiles are a `mg.Grid` of `Fixed` columns centered in it: `tileColumns` fits as many tiles of at least 200 points as the room between `sidebarWidth` and `rightPanelWidth` takes (known from the window's width, as `phoneCenter` sizes the mirror), sharing it up to 232 points each, as the wrapping row did. A last row that is not full starts in the first column. Phones that all fit in one row take one column each, so one row stays centered as before; with three phones the page is laid out exactly as before at 960, 1280 and 1700 points.
- Every tile is built in every frame, so each phone keeps its one stream while the page scrolls. A tile out of view is not painted, so its player converts nothing (`Player.convert` keeps the waiting picture while nobody takes one), and it shows the newest picture as it scrolls into view. Tab reaches tiles out of view, and MyGo scrolls the one it focuses into view.
- The sidebar had the same problem: with a dozen phones in a short window, Add phone, Activity, Settings and Stop all went out of the window. The phones' rows are now a scroll view of their own (`sidebarPhones` in `ui/view.go`) between "Phones" and Add phone, which stays in view with the rest; with few phones nothing moves. A margin and padding of 3 points keep the rows' focus rings from being clipped. When the selection changes, as by a tile of All phones, its row scrolls into view, once.
- No other page had either problem: the other wrapping rows are short rows of buttons or chips, which start at the left, and the long pages already scroll.
